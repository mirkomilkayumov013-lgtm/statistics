# Single-file statistics testing platform

A 3004-line single-file HTML/CSS/JS application implementing an interactive educational statistics platform with 13 task types, trilingual UI, dark mode, score tracking, and localStorage persistence. The architecture splits into seven classes (I18n, MathEngine, DataGenerator, TaskRenderer, AnswerChecker, SolutionDisplay, App) all living in one `<script>` block with no external dependencies.

**Watch for:** Correct answers are stored in DOM `data-answer` attributes, making every answer trivially inspectable via DevTools (confirmed). Interval/histogram tasks can produce intervals where floating-point rounding causes values to fall outside all bins, producing incorrect expected answers (likely). The `checkAnswers()` method accumulates the score on every click without preventing double-submission (confirmed). The t-distribution lookup silently snaps to the nearest of three confidence levels (confirmed).

## High-level view

The statistical engine covers a useful pedagogical range but has precision and correctness issues at the boundaries. The t-distribution lookup table only covers df 1-30 and snaps to the nearest of three confidence levels (0.90, 0.95, 0.99), silently producing wrong critical values for inputs like confidence=0.975. The normal quantile uses Abramowitz & Stegun's approximation, which is adequate for the supported range but the 3-decimal rounding means results can diverge from printed statistical tables students may be comparing against.

Data generation uses uniform random integers for most tasks and Box-Muller for normally-distributed samples, but the histogram and interval series tasks compute interval boundaries with floating-point division that can leave data points uncounted when the range isn't evenly divisible by the interval count. The scoring system has no double-submission guard, so clicking "Check" repeatedly inflates the score.

The internationalization system has full coverage across all 13 task types for three languages, but the solution display steps hardcode English terms ("Sort the sample", "Interval width", "Count values in interval") that bypass the I18n system entirely.

<details>
<summary>Issues (7)</summary>

1. **Score inflation via repeated submission** — `checkAnswers()` adds to `state.score` on every click. Disable the Check button or track per-task submission state to prevent gaming.
2. **Answers exposed in DOM** — Correct answers sit in `data-answer` attributes on every input field. For a testing platform, consider computing answers at check-time rather than render-time, or accept this as inherent to the client-side model.
3. **Floating-point bin gaps in histogram/interval tasks** — Interval boundaries computed via `(max - min) / intervalCount` can produce values where a data point `x` satisfies neither `x >= lower && x < upper` for any bin due to rounding. Validate that all data points are accounted for, or use integer arithmetic for bin edges.
4. **t-distribution snaps to nearest confidence level** — `tQuantile` maps any input confidence to the closest of {0.90, 0.95, 0.99} without warning. Confidence=0.975 quietly returns the 0.95 value. Either interpolate or reject unsupported confidence levels.
5. **Hardcoded English in solution steps** — `solveHistogram`, `solveMedian`, and `solveIntervalSeries` use English strings ("Sort the sample", "Interval width", "Count values in interval") instead of `i18n.t()` calls. These break the trilingual contract.
6. **Timer persists but doesn't pause** — The saved `timerSeconds` is loaded and the timer resumes, but there's no pause/resume. The timer doesn't reflect actual working time if the user closes and reopens the page.
7. **normalQuantile rounding vs. textbook tables** — The 3-decimal rounding in `round()` means quantile values and downstream confidence interval bounds can differ from standard statistical tables by up to 0.001. This matters when students are checking against printed tables.

## Score accumulation without submission guard

The `checkAnswers()` method unconditionally adds results to `this.state.score` on every invocation:

```javascript
checkAnswers() {
    const results = this.checker.checkAllAnswers();
    this.checker.highlightResults(results);
    const scoreResult = this.checker.calculateScore(results);
    if (scoreResult.total > 0) {
        this.state.score.correct += scoreResult.correct;
        this.state.score.total += scoreResult.total;
    }
}
```

Each click re-reads the same inputs and adds to the running total. A student could inflate their score by clicking Check multiple times, including after using "Show Answers" to fill in correct values. The task completion logic (`completedTasks.push`) guards against duplicates, but the numeric score does not.

## Floating-point interval boundary drift

The histogram and interval series tasks compute interval boundaries as:

```javascript
const width = this.math.round((max - min) / intervalCount);
const lower = this.math.round(min + i * width);
const upper = this.math.round(min + (i + 1) * width);
```

Because `width` is rounded to 3 decimal places and then multiplied by the interval index, the final interval's upper bound may not equal `max`. The counting logic for the last interval uses `x <= upper` (inclusive), but if `upper` rounds to less than `max`, data points equal to `max` won't be counted.

Concrete example: min=11, max=79, intervalCount=6. width = round(68/6) = 11.333. The last upper = round(11 + 6*11.333) = round(78.998) = 78.998, which is less than 79. A data point at 79 falls outside all bins, making the expected answer wrong and the student unable to get full marks.

## t-distribution quantile resolution

The `tQuantile` method's confidence-matching logic finds the closest of {0.90, 0.95, 0.99}:

```javascript
const confLevels = [0.90, 0.95, 0.99];
let closestConf = confLevels[0];
let minDiff = Math.abs(confidence - confLevels[0]);
for (const cl of confLevels) {
    const diff = Math.abs(confidence - cl);
    if (diff < minDiff) { minDiff = diff; closestConf = cl; }
}
```

Since `DataGenerator.pickRandom` only generates confidence from [0.90, 0.95, 0.99], this won't trigger with auto-generated data. But the platform's educational value is limited if students can't explore other confidence levels, and the code provides no feedback that unsupported values are being clamped. If the generator is ever expanded, answers will silently be wrong.

## I18n coverage gaps in solution generation

Several solution methods use raw English strings that bypass the translation system:

- `solveHistogram`: `"Interval width"`, `"Count values in interval"`
- `solveMedian`: `"Sort the sample"`, `"Arrange values in ascending order"`
- `solveIntervalSeries`: `"Interval width"`, `"Count values in interval"`

These appear in the step-by-step solution display regardless of the selected language. New I18n keys would need to be added to all three language objects to fix this.
